On Linux, there are several rules that apply to environment variables:


    
	
  1. Every environment variable has a name and a value.
    2. 
	
  2. The name is a sequence of bytes. It may contain any byte except for 0x00 and 0x3D. (In US-ASCII, 0x00 bytes represent NULL characters and 0x3D bytes represent EQUALS SIGN characters).
    3. 
	
  3. The name technically can be zero bytes long, but it’s not a good idea to make it zero bytes long. The setenv() and unsetenv() functions will not work if you create an environment variable who’s name is zero bytes long.
    4. 
	
  4. The value is a sequence of bytes. It may contain any byte except for 0x00.
    5. 
	
  5. The value can be zero bytes long. Unlike zero byte long environment variable names, zero byte long environment variable values won’t break stuff like setenv() and unsetenv().
    6. 



I would like to start by saying that those rules stink. The average user who knows about environment variables thinks that the names and values of environment variables are text. I mean, just look at what happens when you run printenv:


~> printenv | head
CMD_DURATION_MS=3
COLORFGBG=15;0
COLORTERM=truecolor
DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/1000/bus
DESKTOP_SESSION=plasma
DISPLAY=:0
DOCKER_HOST=unix:///run/user/1000/docker.sock
EDITOR=nvim
FLATPAK_TTY_PROGRESS=1
GDK_PIXBUF_MODULE_FILE=/nix/store/pchjc11r13yhlrxi2zjybx4f691xyzg2-gdk-pixbuf-loaders.cache
~> 


That all looks like text to me. When users see stuff like that over and over again, it’s only natural for them to assume that environment variable names and values are text. But they aren’t text! They’re sequences of bytes that may or may not be text. Most of the time, the names and values of environment variables are supposed to be interpreted as text, but in order to interpret a sequence of bytes as text, you need to know its character encoding. But there’s no rule that says that you have to use any particular character encoding! One program could use one character encoding for environment variable names and values, and a different program running on the same system could use a different character encoding for environment variable names and values. And both of those programs would be right to do so! This whole situation is recipe for mojibake.


I don’t like the rules that I listed above, but they are the rules that we’re supposed to play by when dealing with environment variables on Linux. Don’t take by word for it, though. I’m just some random guy on the Internet. I’m not an authoritative source when it comes to environment variables on Linux. That being said, I believe that I can use authoritative sources to prove that the above list rules are accurate.

Proving that rule #1 is true

		

			
An environment variable that has a name must also have a value

			
The Linux man-pages project provides a getenv(3) man page which describes a C library interface. We can use some information from getenv(3) to help prove one of the rules that I wrote previously: “Every environment variable has a name and a value.” That man page says a few different things that are relevant to us:

			
			
We can use the information from that quote to prove that an environment variable that has a name must also have a value. Proving that the statement “an environment variable that has a name must also have a value” is true is an important step towards proving that the statement “every environment variable has a name and a value” is also true. Here’s the proof:

			
    
				
  1. Assume that this statement is true: “an environment variable can have a name without having a value.” (This statement is actually wrong. We’re assuming that it is true so that we can do proof by contradiction.)
    2. 
				
  2. Somehow, add an environment variable to the environment that has the name my_var and does not have a value.
    3. 
				
  3. 
					
    Run getenv("my_var") and inspect its return value.
    
					
      
						
    • If the return value is a pointer to a value in the environment, then that would indicate that my_var really does have a value. This contradicts step #2 because we said that my_var had no value in step #2.
      • 
						
    • If the return value is NULL, then that would indicate that there is no environment variable who’s name matches my_var. This contradicts step #2 because we made is so that an environment variable named my_var really did exist in the environment.
      • 
						
    • If the return value is anything other than those two previous options, then that would contradict the RETURN VALUE section of the getenv(3) man page. The getenv() function is only ever supposed to return a pointer to a value in the environment or NULL.
      • 
					
    
				
    4. 
				
  4. This indicates that the following statement from step #1 must not be true: “an environment variable can have a name without having a value.”
    5. 
				
  5. Therefore, the following statement must be true: “an environment variable that has a name must also have a value”
    6.
